**Headline findings**
- **Approval gate bypass.** `POST /api/posts/[id]/publish` publishes a DRAFT with no status check, and the UI exposes the button on every unpublished post.
- **Stuck posts.** A worker crash or timeout leaves a post in `PUBLISHING` forever. Lease recovery does not fix it, and the post then cannot be edited or deleted.
- **Double-post window.** A crash between the platform send and the DB write re-sends the post on retry. No platform-side idempotency key exists.
- **Approval is self-approval only.** Every post query is scoped by `post.userId`, so an approver cannot see an editor's submitted post.

## 1. What the app really is

A Next 16 / React 19 / Prisma 7 / NextAuth v4 (JWT) multi-account social publishing tool with an approval workflow (`package.json`). Users sign in, connect social accounts (OAuth or a Telegram bot token) and draft posts. Roles (ADMIN/MANAGER/EDITOR/CLIENT, `src/lib/roles.ts:60-73`) gate submit/approve/schedule. A 5-minute Vercel cron (`vercel.json:4-5`) publishes scheduled posts through per-platform adapters. Around that core sit:
- BYO-key AI drafting and a "brand brain" with ingest/embed/retrieve modules (`src/lib/brain/*`);
- an engagement API for comments and reactions;
- a small "native network" (feed, reactions, comments, profile);
- five fixture-driven "intelligence" widgets that are labelled mock.

The multi-tenant layer is only half-wired (Section 4).

## 4. Security and authorization

I read most routes in full; for `brand-brain`, `experiments` and `growth-brief` I confirmed the session check by grep only. Post, account, media and engagement queries are scoped by `userId`. I found **no cross-tenant read path** in the routes read. The gaps are authorization, races and trust of client-held data.

**4.1 Gate bypass: publish route.** See Section 5.

**4.2 Approval is self-approval only.**
- `approve/route.ts:27-29`, `schedule/route.ts:34-36`, `reschedule:35-37` and `retry:45-47` all query `findFirst({where:{id, userId: guard.userId}})`.
- A MANAGER therefore gets 404 on an EDITOR's `PENDING_APPROVAL` post, because `post.userId` is the editor.
- The only user who can approve a post is its author, so the editor→manager flow does not work across users.
- `roles.e2e.mjs:269-281` exercises approve only against a non-existent post id, so this is never tested.

**4.3 Tenancy is half-wired.**
- Brains and the accounts list are workspace-scoped (`brains.ts:28-33`, `accounts/route.ts:20-25`). Posts, accounts-for-publish, media, engagement and inbox are user-scoped.
- Teammates see accounts they cannot publish through (`publish/route.ts:74`).
- `brains` GET lists by `userId` (`brains/route.ts:17`) but DELETE resolves by workspace.
- `WorkspaceMember.role` is recorded and never consulted (`workspace.ts:5-9`, `workspace-role.ts:20-24`).
- There is no invite or add-member route in `src/app/api`. Multi-user workspaces exist only via the backfill script.

**4.4 Session-only mutating routes (no permission check).**
- **`inbox` PATCH** (`inbox/route.ts:81-140`): reply/markAsRead need only a session, so a CLIENT passes. This is harmless in production today because real replies return "Not implemented". It is live in mock mode.
- **Media** (`media/route.ts:41-43`, `finalize:32-34`, `upload-token:22-24`): any signed-in role, including read-only CLIENT, can issue Blob upload tokens up to 500 MB (`blob-upload.ts:MAX_UPLOAD_BYTES`) and write assets.
- **Brains** (`brains/route.ts:34-37`, `brains/[id]/route.ts` DELETE/PATCH): no role check. Any member, including a CLIENT, can delete a brain and reassign all of the workspace's accounts (`brains/[id]/route.ts` DELETE).
- **`brand-brain`** POST/PUT: session only.

**4.5 OAuth state cookie is unsigned.**
- `connect/route.ts:79-85` stores `{userId,platform,brainId,...}` as plain JSON, and `state.ts:80` `JSON.parse`s it with no HMAC.
- `callback.ts:42` checks only that a session exists. It never calls `requirePermission("accounts:connect")`.
- A CLIENT can hand-craft the cookie (its own `userId`) and complete provider authorization against the app's public client id, then connect an account without ever calling `/connect`. This needs a real provider account. I did not execute it, so it is plausible rather than proven.
- The state cookie is deleted only on success (`callback.ts:178`).

**4.6 Telegram connect.**
- `telegram/connect/route.ts:20` is a state-changing `GET`. Session cookies are Lax, so a cross-site top-level navigation carries them.
- `chatId` comes from the query (:76) and is accepted if `getChat` succeeds (:97-103). The existing account's `metadata.chatId` is overwritten on upsert (:147-155).
- A CSRF link can therefore re-point an owner's Telegram account at an attacker-controlled chat that already contains the shared env bot. The mechanism is by reading; I did not reproduce it.
- Related: one shared bot token from env means the first tenant to connect owns it (:110-125).

**4.7 Roles and sessions.**
- The role is frozen into the JWT at login (`auth.ts:241-249`). Demoting a user does not revoke rights until the token expires.
- The session callback defaults to `DEFAULT_ROLE` (ADMIN) when `token.role` is invalid (:234), against the least-privilege `FALLBACK_ROLE = "CLIENT"` (`roles.ts:40`). The jwt callback normally sets the role, so this fires only on a malformed token.
- `ai/credentials` workspace scope checks membership (:91-101) and then `users:manage` from the global `User.role` (:106). It does not check the member's workspace role.

**4.8 Check-then-act races** (none uses a conditional `updateMany`):
- `schedule/route.ts:43` reads APPROVED, then `:68-70` updates by `id` only. A concurrent PATCH (`posts/[id]/route.ts:116-121`, which resets to DRAFT and clears approval) can be overwritten, leaving unapproved edited content `SCHEDULED`.
- `approve/route.ts:35` vs `:43-45` has the same shape.
- `cron/publish/route.ts:155` checks SCHEDULED, then `:217` sets PUBLISHING unconditionally. Content edited in between is published.
- `publish/route.ts:49` then `:151-154` is non-atomic, so a double-click can double-send.

**4.9 Other.**
- **Registration:** no rate limiting on login or register (grep for rate-limit finds only error taxonomy and engagement files, not throttling). Register reveals whether an email exists (`register/route.ts:49-53`). The first-user check is racy (:61, :79).
- **Encryption:** CryptoJS passphrase AES is unauthenticated, and `decrypt` returns `""` on a wrong key instead of throwing (`encryption.ts:46-53`). Publishing would then proceed with an empty token.
- **Media provenance:** `finalize` trusts client `mimeType`/`size` and does not pin the Blob store (`blob-upload.ts:12-18` admits this). `media/route.ts:99` puts the client-supplied `file.name` in the blob path; sanitisation is **UNVERIFIED**.
- **Media deletion:** `DELETE /api/media` (:136-160) deletes the row and never removes the blob (no `del` call in the file).
- **Client-supplied ids that are checked:**
  - `socialAccountId` is checked at `posts/route.ts:96-105`, `posts/[id]/route.ts:94-102`, `publish:74` and `cron:193`.
  - `brainId` is checked at `brains.ts:77-79`, which silently falls back to the default brain.
  - Media ids are checked via `unownedMediaAssetIds`.
  - Engagement `accountId` is checked via `loadOwnedAccount`.
- **Unchecked or loose ids:**
  - Inbox PATCH picks the first active account for the platform and ignores which account owns `itemId` (`inbox/route.ts:98-109`).
  - `experiments` accepts an arbitrary `subjectId` (:43), probably harmless (**UNVERIFIED**).
- **Cron secret:** compared with `===` (`cron-auth.ts:12`), not timing-safe, and it fails closed when unset. Low risk.
- **Secret handling in responses:** `PUBLIC_SOCIAL_ACCOUNT_SELECT` / `POST_SAFE_INCLUDE` (`account-select.ts:16-44`) keep tokens out of post and account responses. `health` returns env variable names only (`health/route.ts`).

## 5. The approval gate

**Enforcement points**
- **Creation:** `posts/route.ts:137` creates every post as DRAFT. `cascade/route.ts` creates drafts only.
- **Edit invalidates approval:** `posts/[id]/route.ts:116-121` sets DRAFT, clears `approvedAt`/`approvedBy` on every PATCH. Edits to PUBLISHING/PUBLISHED are blocked at :82.
- **Submit/approve/reject:** `approve/route.ts:19-22` (per-action permission), :35 (only DRAFT/PENDING_APPROVAL), :43-50 sets APPROVED.
- **Schedule:** `schedule/route.ts:43-48` is the only place that sets SCHEDULED from APPROVED, returning 400 otherwise. Reschedule requires SCHEDULED (`reschedule:44`). Unschedule returns to APPROVED (`schedule:134-148`).
- **Retry:** `retry/route.ts:54-60` uses `failed-retry/index.ts:16-27`: must be FAILED, have `approvedAt` and an account. It is the only other path to SCHEDULED.
- **Disconnect:** `accounts/route.ts:157-161` moves SCHEDULED to APPROVED, never forward.
- **Worker:** `cron/publish/route.ts:155-167` publishes only `post.status === SCHEDULED`; anything else fails the job.

**Proof for DRAFT → SCHEDULED:** the only writers of `PostStatus.SCHEDULED` are `schedule:71` (guarded by :43) and `retry:79` (guarded by `approvedAt` + FAILED), plus the worker's own retry reset at `cron:469` (only reachable from a post it just published). A grep of `src` for `PostStatus.(SCHEDULED|APPROVED|PUBLISHED|PUBLISHING)` outside dashboard UI and cron confirms no other writer. In code, DRAFT → SCHEDULED through the scheduling routes is impossible.

**Gaps**
1. **Publish route bypasses the gate (blocker).** `publish/route.ts:26-47` requires only `posts:schedule`. It never checks `status === APPROVED`/`SCHEDULED` or `approvedAt`. The only blocks are `platformPostId` (:42) and PUBLISHING (:49).
   - A DRAFT or PENDING_APPROVAL post goes PUBLISHING (:151) then PUBLISHED (:189-199) with no approval.
   - `post-card.tsx:193-195` renders `PublishNowButton` for every post without `platformPostId`, so the UI exposes it on drafts.
   - It contradicts `AGENT-BRIEF.md:28-30` ("only scheduled content is published").
   - No test calls this route (grep of `tests/`).
2. **Self-approval is unrestricted** (Section 4.2). Author and approver are always the same user, and there is no maker-checker.
3. **TOCTOU on status** (Section 4.8).
4. **No DB-level guard.** `PostStatus` is a plain enum (`schema.prisma:277`) with no constraint or state-machine function, so each route re-implements its own check.
5. **The only unit test of the gate is a tautology.** `tests/unit/schedule-gate.test.ts:5-14` defines its own local `canSchedule()` and asserts on it; it never imports the route. Real enforcement coverage is the e2e check 8 (`tests/e2e/README.md`), which needs Postgres (Section 7).

## 6. Publishing worker and job queue

**What holds**
- **Atomic claim:** `updateMany` PENDING→PROCESSING with `attempts` increment (`cron:103-115`). The loser skips.
- **Retry/backoff:**
  - `MAX_ATTEMPTS = 3`, base 30 s, cap 15 min (`cron:30-37`).
  - Permanent error codes dead-letter on attempt 1.
  - `UNKNOWN` is treated as retryable (`:455-463`).
  - Failures update post and job in one transaction (`:465-495`).
- **Dead-letter:** exhausted jobs are `JobStatus.FAILED` and the post is FAILED with the error preserved (`:469-482`). There is no separate DLQ table.
- **Dedupe:** a post with `platformPostId` completes its job without re-sending (`:142-153`).
- **Ownership:** `account.userId !== post.userId` fails the job (`:193-215`).
- **Credential state:** a successful publish clears `needsReconnect` (`:378-380`); credential failures set it (`:487-494`).

**Defects**
1. **Cron dies mid-publish: the post is stranded in PUBLISHING forever.**
   - The worker sets the post PUBLISHING (`:217`) and the job PROCESSING (`:103`).
   - After a 10-minute lease (`lease-recovery.ts:27`), recovery returns the job to PENDING (`:64-71`) but does not touch the post.
   - The next run claims it and hits `post.status !== SCHEDULED` (`cron:155`), so the job becomes FAILED "Invalid post status: PUBLISHING" and the post stays PUBLISHING.
   - Nothing else clears PUBLISHING. Publish rejects it (`publish:49`), PATCH blocks edit (`posts/[id]:82`) and DELETE refuses (`:199`), so the post is undeletable.
   - This contradicts the comment at `lease-recovery.ts:4-8`.
   - `durability.mjs` has no PUBLISHING-recovery case (grep). `mvp-honesty.test.ts` mentions lease and I did not read it.
2. **Double-post window.**
   - No adapter passes a platform idempotency key (grep for idempotenc/request-id in `src/lib/adapters` returned nothing).
   - The only dedupe is `platformPostId` (`cron:142`), which is written after the send (`:321` → `:362`).
   - A crash or DB error in that window, then a reclaim or retry, re-sends. The outer catch (`:399-411`) also schedules a retry for an error thrown after a successful send.
   - This violates `AGENT-BRIEF.md:83-84`. It holds only when the DB write completes.
3. **Immediate publish has no queue or recovery.** `publish/route.ts` runs inline with no job. A timeout or crash strands the post (defect 1), and the PUBLISHING lock is non-atomic (`:49` / `:151`).
4. **Throughput and timeout.**
   - It takes 10 jobs per run, sequentially (`cron:94`), every 5 minutes (`vercel.json:5`), so effective retry spacing is at least 5 minutes, not the 30 s / 60 s in the constants.
   - No `maxDuration` is set anywhere in `src` (grep). The platform default function timeout is **UNVERIFIED**; slow video uploads could be cut off, producing defect 1.
5. **Disconnect race.** `accounts/route.ts:146-153` deletes PENDING and PROCESSING jobs, including one mid-send; the post's PUBLISHING state is not handled.
6. **Success without an id.** If an adapter returns success without `platformPostId`, `cron:368` stores undefined and dedupe never triggers. Which adapters do this is **UNVERIFIED**.

## 8. Top 10 risks (ranked by real impact)

1. **Publish route skips approval.** `publish/route.ts:33-47`, `post-card.tsx:193`. Fix: require `status===APPROVED` (or SCHEDULED) and `approvedAt`, and claim atomically with `updateMany({where:{id,status}})`; hide the button for non-approved posts.
2. **Posts stranded in PUBLISHING.** `cron/publish/route.ts:155`, `lease-recovery.ts:70`, `posts/[id]/route.ts:199`. Fix: recovery also resets the post to SCHEDULED (or the worker accepts PUBLISHING for a reclaimed job), and add a stale-PUBLISHING sweep.
3. **Double-post on crash between send and DB write.** `cron:321-362`. Fix: record a send intent or idempotency token before sending, pass it to platforms that support one, and on reclaim mark for review instead of auto-resending.
4. **Approval only works for the author.** `approve:27-29`, `schedule:34-36`. Fix: scope by `requireWorkspace()`'s `workspaceId` and add a maker-checker rule (approver ≠ author) if wanted.
5. **Unsigned OAuth state cookie bypasses `accounts:connect`.** `state.ts:80`, `connect:79`, `callback.ts:42`. Fix: HMAC-sign the cookie and call `requirePermission("accounts:connect")` in the callback.
6. **Telegram GET CSRF, attacker-chosen chat.** `telegram/connect/route.ts:20,76-103,147-155`. Fix: make it POST with a CSRF token and require proof of chat ownership.
7. **Status races.** `schedule:43→68`, `approve:35→43`, `cron:155→217`. Fix: conditional `updateMany` with a status in `where`, and return 409 when `count===0`.
8. **Stale and over-broad roles.** `auth.ts:234,241-249`, `requirePermission:288`. Fix: read the role from the DB (or use a short JWT `maxAge`), fall back to `FALLBACK_ROLE`, and use the workspace role.
9. **Missing permission checks on mutating routes.** `inbox:81-140`, `media/*`, `brains/*`, `brand-brain`. Fix: add `requirePermission` (`engagement:reply`, `posts:create`, `accounts:connect`) and role cases in `roles.e2e.mjs`.
