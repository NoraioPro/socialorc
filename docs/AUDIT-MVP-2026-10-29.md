## Report A — Executive Summary

**MVP readiness: NOT READY for external users.** The core loop (register → connect account → draft → approve → schedule → publish) is genuinely implemented and persisted, and the publish worker is carefully built. But the multi-user model is unsound (global roles, a privilege-escalation path in OAuth sign-up, no workspace scoping), and no platform has been proven to publish for real.

### Five most serious verified deficiencies

1. **OAuth sign-up yields an ADMIN session (A-01, P0).** Spot-checked: `prisma/schema.prisma:87` defaults `User.role` to `"ADMIN"`; the `createUser` event (`src/lib/auth.ts:67`) corrects the DB row *after* creation, but the `jwt` callback (`src/lib/auth.ts:255-258`) copies `user.role` from the pre-correction adapter object. The first token for a new Google/Facebook user therefore carries ADMIN until it expires (no `maxAge` set, so next-auth's 30-day default). Code path confirmed; not reproduced at runtime. Only exploitable if Google/Facebook sign-in is configured.
2. **Global admin endpoints with no tenant scope (A-02, P0 when combined with A-01).** `/api/workspace/users` and `/api/workspace/invitations` list/modify *every* user and invitation in the deployment, gated only by global `User.role === "ADMIN"`.
3. **Team collaboration does not work (A-05/A-06/A-17, P1).** Every data query filters by `userId`, there is no workspace switcher, invitations create a *separate* workspace for the invitee, and approvals only work on one's own posts. "Team" is cosmetic.
4. **Publishing can duplicate or strand posts (P-01/P-02/P-03, P1/P2).** Reschedule races the worker; a thrown error after a send is retried (possible double post); publish-now can leave a post stuck in PUBLISHING forever.
5. **No platform is verified end-to-end (P-D1, P1).** Only LinkedIn, X and TikTok credentials exist locally; Facebook, Instagram, YouTube, Telegram and Blob tokens are unset. TikTok direct posting needs a platform audit. Nothing was ever published to a real network in evidence available here.

### Already functional (code-verified; not live-verified)
Credentials sign-up/login (bcrypt, rate-limited, invite-only default); OAuth state (signed, TTL, PKCE for X/TikTok); token fields stripped from API responses; post state machine with guarded `updateMany`; approval gate in routes; cron auth fails closed; lease recovery for stuck jobs; schedule timezone handling; AI generate/improve via the customer's own key; Blob direct upload; 667 unit tests pass; `tsc` and `eslint` clean (0 errors).

### External dependencies blocking release
- LinkedIn "Share on LinkedIn" product approval (self-serve) — needed for the recommended first platform.
- Meta App Review (`pages_manage_posts`, `instagram_content_publish`) for Facebook/Instagram.
- TikTok audit for direct posting (drafts only until then).
- Google OAuth verification for YouTube public use.
- A cron host: Vercel Pro (`*/5` is rejected on Hobby) or an external scheduler.
- Vercel Blob token (or equivalent public HTTPS storage).

### Key unknowns
Production env values (CRON_SECRET, TOKEN_ENCRYPTION_KEY, OAUTH_STATE_SECRET, OAuth providers, signup policy); live DB contents and drift; Supabase tier/backup state; whether `next/og` is used (affects the Next advisory); whether any real publish has ever succeeded.

## Scheduler decision (needs owner input — no infrastructure was changed)

Current mechanism: Vercel Cron `*/5 * * * *` → `GET /api/cron/publish` with `Bearer CRON_SECRET` (fails closed if unset). It runs independently of any browser, claims jobs atomically, has lease recovery (plus, now, the publish-now reaper), and ambiguous sends are no longer retried. Smallest option: keep Vercel Cron if already on Pro; otherwise a host cron calling the endpoint every minute at no extra cost.

## Signup policy as the code behaves (`src/lib/signup-policy.ts`, `register/route.ts`, `auth.ts`)
- **Password signup:** allowed if it is the first account, `ALLOW_PUBLIC_SIGNUP=true`, the address is in `SIGNUP_ALLOWLIST`, or a valid invitation is presented. Otherwise 403.
- **Google sign-in (live in Production):** a new identity goes through the same decision in the `signIn` callback (Phase 1). Existing users and already-linked identities are never blocked by it.
- **So `ALLOW_PUBLIC_SIGNUP=true` opens both password and Google signup**, and `false` closes both (except first account, allowlist, invitations).

## Blocker found and fixed: public signups could not use the product
Every signup after the first got global role **EDITOR** (`selfSignupRole`, `OAUTH_SIGNUP_ROLE`). EDITOR lacks `accounts:connect`, `posts:approve` and `posts:schedule` (`roles.ts` matrix), so no public user could connect an account, approve, schedule or publish. The e2e harness forced `SIGNUP_ROLE=ADMIN`, which hid it. Each self-signup owns a private workspace and every ADMIN power (`users:manage`, `posts:delete`, workspace AI keys) is scoped to the caller's workspace (`requireWorkspace`; verified in `workspace/*`, `ai/credentials`, `posts/[id]`), so the default is now **ADMIN of the user's own workspace** for password and Google signups. Safe only while teams stay off (roles are still global, N-9); revisit before enabling teams. Also: a DRAFT can now be approved directly from the draft page by an approver, and an approved post links to the Queue to schedule/publish (previously Submit → Approve → find Queue).
Tests: `tests/unit/self-signup-role.test.ts` (6).

## Platform reality for public users (app-level approvals, not per user)
LinkedIn needs the "Share on LinkedIn" product on the app; X free-tier write quota is shared across all users of the app; **YouTube** (unverified Google app: test users only) and **TikTok** (unaudited: drafts only) will not work for the public. They appear connectable because their credentials are set. Hide them without code by removing the `YOUTUBE_*` and `TIKTOK_*` Production variables until approved.
